# Диагностика Amnezia VPN

Исторический журнал первичной диагностики. Описанные в начале ограничения и неподтверждённые действия относятся к ранним этапам. Последующий рабочий результат XRay через мобильную сеть и Wi-Fi описан в [итогах проверки VPN](vpn-working-path-20261122.md).

Дата: 21 ноября 2026 года.

## Подтверждено

- На предоставленном снимке открыта SSH-сессия Termius. Вход на сервер выполнен; показано уведомление о необходимости перезагрузки.
- Само уведомление о перезагрузке не доказывает причину отказа VPN.
- Локальный репозиторий содержит установщик 3x-ui и MTProxy. Он не подтверждает фактическую конфигурацию удалённого сервера и не запускался.
- Прямое SSH-подключение остановилось на проверке подлинности сервера: локальному OpenSSH неизвестен ключ ED25519 этого узла. Аутентификация пользователя и диагностические команды не выполнялись.
- Настройки сервера и VPN не менялись. Перезапусков, установки пакетов и изменений firewall не было.

## Ограничение управления Termius

Навык computer-use запрещает автоматизацию терминальных приложений: «Do not automate terminal applications such as Windows Terminal, Command Prompt, or Windows PowerShell». Поэтому команды через окно Termius не вводились.

## Следующий шаг

В уже открытой SSH-сессии пользователь может выполнить команды только для чтения:

```bash
uptime
docker ps -a --format '{{.Names}} | {{.Status}} | {{.Image}}'
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Первые две команды покажут состояние сервера и контейнеров. Третья покажет отпечаток публичного ключа сервера для проверки отдельного SSH-подключения. Приватный ключ и пароль передавать не нужно.

## Полученные результаты

- По выводу пользователя сервер работает 13 дней; нагрузка на момент проверки невысокая.
- amnezia-awg2, amnezia-telemt и amnezia-xray имеют статус Up 13 days. Это подтверждает запуск контейнеров, но не работоспособность VPN внутри них.
- Контейнеры Loki, Promtail и Grafana остановлены с кодом 137. Этот код сам по себе не доказывает нехватку памяти; связь с проблемой VPN не установлена.
- Пользователь предоставил отпечаток ED25519 через существующую SSH-сессию. Следующая попытка получить публичный ключ через ssh-keyscan завершилась без ключа, с кодом 1. Причина недоступности этим результатом не определяется.

Причина отказа Amnezia пока не установлена. Исправления необходимо согласовать с пользователем после получения диагностических данных.

## Проверка сети по выводу пользователя

- amnezia-awg2 публикует UDP 46872, amnezia-xray — TCP/UDP 443. У обоих RestartCount=0 и OOMKilled=false.
- В контейнере AWG есть интерфейс awg0 с адресом 10.8.1.0/24 и маршрут по умолчанию через eth0. Статус UNKNOWN у туннельного интерфейса сам по себе не означает неисправность.
- Контейнер AWG подключён к двум сетям: через eth0 и eth1. Это требует проверки NAT, но само по себе не является доказанной ошибкой.
- На хосте net.ipv4.ip_forward=1. UFW активен; UDP 46872 и TCP/UDP 443 разрешены для входящих подключений.
- Политика UFW deny (routed) требует сопоставления с фактическими правилами Docker и счётчиками пакетов. Делать вывод о блокировке только по этой строке нельзя.
- Следующая проверка: handshake и счётчики AWG, пересылка и NAT внутри контейнера. Секретные ключи и полные VPN-конфигурации запрашивать не требуется.

## Прямая диагностика по SSH

- После подтверждения пользователем ключа сервера прямой SSH-доступ заработал.
- Пересылка IPv4 внутри AWG включена. В контейнере есть MASQUERADE для VPN-подсети и разрешающие правила FORWARD со счётчиками ранее проходившего трафика.
- Проверка 1.1.1.1 из AWG-контейнера успешна: 3 ответа из 3, около 6 мс.
- На момент проверки 08:00–08:03 UTC свежих handshake нет. Самый новый из имеющихся — около 11 часов назад. После сообщённой пользователем попытки с телефона через мобильную сеть время handshake не обновилось.
- На Windows активен ulta-vpn-tun; выбранный маршрут к VPN-серверу проходит через него. Также активен адаптер Fortinet. Это отдельный фактор на Windows, но он не объясняет автоматически сбой телефона.
- Контрольный UDP-пакет с Windows в 08:04:14 UTC зафиксирован на внешнем интерфейсе сервера и после DNAT на мосте Amnezia с назначением в AWG-контейнер. Следовательно, полная недоступность UDP-порта для всех источников и безусловная блокировка этого пакета на хосте не подтверждаются. Это не проверяет доставку из мобильной сети и не является успешным VPN-handshake.
- Для продолжения нужно сопоставить адрес и порт проблемного профиля телефона с фактическим сервером и наблюдать именно его попытку подключения.

Все проверки выполнялись без изменения VPN, firewall, маршрутов и конфигурации сервера. Отправлялся один диагностический UDP-пакет за попытку; содержимое пользовательского трафика не запрашивалось.

По указанию пользователя отчёты Markdown и отдельные файлы настроек этой задачи сохраняются в текущем репозитории VpsSettings; секреты в репозиторий не записываются.

## Проверка после скриншота телефона

- На скриншоте выбран адрес проверяемого сервера и AmneziaWG version 3.1. Отображается «Подключение…», а не установленное соединение. Порт на скриншоте не виден.
- Серверные инструменты сообщают amneziawg-tools v3.1.20260812. Контейнер слушает UDP 46872 на IPv4 и IPv6; ошибка состояния Docker отсутствует.
- За 25 секунд последующего наблюдения tcpdump на внешнем интерфейсе не зафиксировал ни одного пакета UDP 46872. Handshake остались прежними.
- Установлено отсутствие входящего трафика на проверяемый порт в этом интервале. Причина не установлена: необходимо проверить порт профиля и учитывать возможность прекращения попыток приложением, сетевой фильтрации либо проблем клиента. Утверждать доказанную блокировку провайдером нельзя.
- Перезапуск контейнера или изменение UFW пока не обоснованы полученными данными. Настройки не менялись.

## Сопоставление параметров и альтернативный протокол

- На втором скриншоте телефона порт 46872, S1–S4 равны 12, H1–H3 равны 1, 2, 3.
- Выборочное чтение несекретных полей работающего awg0 подтвердило совпадение этих параметров. Дополнительно сервер сообщает Jc=4, Jmin=10, Jmax=50 и H4=4; соответствующие поля телефона на скриншоте не видны.
- Поэтому ошибка видимых параметров профиля не обнаружена. Полное совпадение профилей и ключей не проверено. Отсутствие пакетов на внешнем интерфейсе не объясняется несовпадением ключей внутри сервера.
- Уже установленный amnezia-xray работает без рестартов, слушает TCP 443; проверка 1.1.1.1 из контейнера успешна, 2 из 2 ответов.
- Предложен контрольный переход телефона на существующий XRay без переустановки сервера и изменения AWG. Успешность клиентского подключения XRay ещё не проверена. Изменение выбранного протокола ожидает согласия пользователя.

## Гипотеза сетевой фильтрации

Пользователь предложил проверить влияние ТСПУ. Это правдоподобная гипотеза фильтрации в сети между клиентом и сервером, а не доказанная неисправность приложения.

Факты совместимы с выборочной фильтрацией: контрольный произвольный UDP-пакет через другой VPN дошёл, тогда как в отдельные интервалы попыток телефона пакеты на целевом порту не наблюдались. Но сравнивались разные источники и разные виды пакетов. Такие результаты не доказывают работу ТСПУ и не исключают прекращение отправки клиентом либо другую сетевую причину. SSH с Windows также проверялся через ulta-vpn-tun, поэтому его доступность не подтверждает прямую доступность сервера из мобильной сети.

Официальная инструкция Amnezia рассматривает блокировку IP и параметров протокола среди причин отказа self-hosted AmneziaWG и предлагает сравнение через другую сеть:
https://docs.amnezia.org/troubleshooting/self-hosted-amneziawg-not-working/

Предпочтительная следующая проверка без изменения сервера — сравнить тот же профиль на независимых интернет-подключениях с наблюдением на сервере. Успешный XRay при неработающем AWG будет дополнительным признаком выборочного ограничения либо проблемы AWG, но сам по себе не определит конкретное фильтрующее оборудование.

## Уточнение пользователя и предлагаемый тест I1

Пользователь уже проверял несколько сетей. Повторное предложение просто сменить сеть не учитывало этот факт. ПК использует другой VPN, поэтому контрольная доставка UDP с ПК проверяет другой сетевой путь и не подтверждает доступность AWG напрямую.

Выборочная проверка /opt/amnezia/awg/awg0.conf подтвердила Jc=4, Jmin=10, Jmax=50, S1–S4=12, H1–H4=1–4. Строк I1–I5 в этом файле не обнаружено. Это не доказывает отсутствие I1 в клиентском профиле и само по себе не доказывает ошибку сервера.

В разделе Changing the Signature официальной инструкции предлагается заменить I1 только в настройках подключения текущего устройства. Это отличается от изменения серверных настроек: инструкция предупреждает, что сохранение серверных настроек переустанавливает контейнер и требует пересоздать пользователей. Такой серверный вариант не предлагается.

Подготовлено значение из официальной инструкции: [i1-candidate.txt](../../config/amneziawg/i1-candidate.txt). Это публичная тестовая сигнатура, не пароль и не VPN-ключ. Она пока нигде не применена.

План после согласия пользователя:

1. На одном телефоне сохранить исходное значение I1 отдельно для отката. Не передавать приватные ключи и не экспортировать весь профиль.
2. Открыть именно настройки подключения AmneziaWG текущего устройства, а не настройки протокола на сервере.
3. Заменить только I1 значением из подготовленного файла и переподключиться.
4. Одновременно проверить на сервере поступление UDP-пакетов, свежий handshake и работу интернета на телефоне.
5. Если тест не помогает, вернуть прежнее I1. Сервер, порт, пользователи и остальные параметры при этом не меняются.

Тест не гарантирует обход фильтрации и не доказывает наличие ТСПУ даже при успехе. Если в приложении нельзя однозначно отличить настройки подключения от серверных, перед сохранением требуется проверить экран.

Источник: https://docs.amnezia.org/troubleshooting/self-hosted-amneziawg-not-working/#changing-the-signature

Пользователь разрешил тест замены I1 на одном телефоне. Разрешение не распространяется на переустановку протокола, изменение серверных параметров или пересоздание пользователей. Изменение пока не применено: необходимо открыть клиентские настройки подключения и сохранить исходное значение I1. Ранее присланный экран содержит раздел «Настройки сервера» и для этого теста не подходит.

Пользователь передал исходное значение I1; оно сохранено без изменений в amneziawg-i1-original.txt. Переданная строка содержит только hex с префиксом 0x, без синтаксического обрамления. Полнота исходного выражения I1 не подтверждена: на скриншоте виден закрывающий символ >, отсутствующий в переданном тексте. Для точного отката следует сохранить полное содержимое поля на телефоне, включая обрамление, если оно есть. Замена и сохранение на телефоне пока не подтверждены.

## Результат согласованного теста I1

Пользователь подтвердил сохранение новой сигнатуры на телефоне. При попытке подключения сначала сообщалось «Подключение…», затем «Подключено», однако сайт не открывается.

Наблюдение на сервере в интервале Unix 1795250208–1795250258: за 50 секунд tcpdump на eth0 не зарегистрировал пакетов UDP 46872; времена handshake и счётчики передачи AWG не изменились. Статус приложения не подтверждается успешным туннелем на сервере. Исправление не достигнуто; сигнатуру нельзя считать рабочей по этому тесту.

Следующий предлагаемый шаг — вернуть сохранённое полное исходное I1 и проверить уже установленный XRay на одном телефоне с наблюдением TCP 443. Это отдельное переключение протокола требует согласия пользователя. Серверные настройки в ходе теста I1 не менялись.

На IMG_2634.PNG открыт экран добавления подключения: доступны вставка ключа, импорт файла и QR-кода. Пункт «VPN на своём сервере» для текущего теста не использовался.

Официальная инструкция подтверждает импорт конфигураций через файл или текстовый ключ: https://docs.amnezia.org/documentation/instructions/connect-via-config/

Для самостоятельной подготовки импорта существующего доступа потребуется конфиденциальный клиентский файл. Перед его сохранением в папку проекта необходимо явно согласовать с пользователем это исключение из запрета хранения секретов и исключить файл из Git. В клиентский файл не должен попадать приватный REALITY-ключ сервера или SSH-доступ.

## Экспорт XRay после согласия

Пользователь явно разрешил сохранить клиентский доступ в приватную папку текущего проекта, исключённую из Git.

- Добавлено правило /private-vpn/ в .gitignore; git check-ignore подтверждает исключение обоих файлов. Среди отслеживаемых файлов private-vpn отсутствует.
- Созданы private-vpn/configs/original/xray-phone.json и private-vpn/configs/original/xray-phone-link.txt. Они конфиденциальны: содержат доступ существующего пользователя XRay. Это не отдельный новый пользователь; отзыв или изменение его доступа затронет и другие устройства, использующие того же пользователя.
- Публичный REALITY-ключ вычислен на сервере из приватного; приватный REALITY-ключ и SSH-доступ в файлы не экспортировались.
- Клиентский JSON успешно проверен командой Xray run -test внутри существующего контейнера через стандартный ввод. Это проверка корректности конфигурации, а не успешного соединения с телефона.
- Содержимое server.json до и после экспорта совпало. Настройки сервера не менялись; контейнер не перезапускался; новые пользователи не добавлялись.

Действия пользователя: перенести xray-phone.json на телефон приватным способом, открыть Amnezia → плюс → «Файл с настройками подключения» и выбрать этот JSON. После импорта сообщить о готовности до подключения, чтобы согласовать окно наблюдения на сервере. Если импорт JSON не поддерживается конкретной версией приложения, запасной вариант — импорт строки из xray-phone-link.txt через поле вставки ключа. Файлы и их содержимое в чат или публичные сервисы не отправлять.
