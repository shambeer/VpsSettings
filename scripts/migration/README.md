# Развёртывание и миграция VPN

Точка входа — [migrate.py](migrate.py). Сценарий запускается на вашем компьютере, работает с Linux-серверами через системные ssh/scp и не отправляет приватный SSH-ключ на сервер. Запуск не выполнялся при разработке: готовность на конкретном VPS подтверждается только испытанием ниже.

## Запуск

### Продолжение после обрыва или закрытия программы — FR-07

Новые операции автоматически создают приватный `session.json` в выбранной папке результатов. Сразу после выбора папки мастер печатает готовую команду продолжения; она также сохраняется в поле `resume_command` этого файла. При ошибке/отмене команда печатается повторно.

```text
python scripts/migration/migrate.py --resume "/путь/к/папке/операции/session.json"
```

Для Windows используйте готовую строку из `resume_command`: в ней уже правильно заключены пути с пробелами. Введите **RESUME**, чтобы продолжить ранее согласованную операцию. Сохранённые ответы восстанавливают тот же сценарий и те же серверные каталоги; выполненные этапы и подтверждённые загрузки не запускаются заново. Ещё не полученные подтверждения запрашиваются как обычно. Неверное подтверждение не сохраняется как разрешение.

Поддерживаются новая установка, восстановление, создание копии и обслуживание, включая схему двух VPS. Если закрыть мастер во время создания исходной копии для миграции, продолжение сначала закончит эту копию, затем запросит оставшиеся параметры нового сервера. До сохранения папки результатов удалённые действия не начинаются; незавершённый ввод до этой точки можно просто повторить.

Серверные backup/deploy/relay/maintenance-apply запускаются через systemd. При потере ответа на запуск мастер проверяет то же имя unit и серверную отметку выполнения, а не создаёт другую задачу. Серверная блокировка и постоянная отметка запрещают повторное выполнение того же задания. Если исходный процесс остановлен без результата (например, VPS аварийно перезагрузился), программа сообщает об этом и не повторяет потенциально частичные изменения автоматически. Возобновление после потери SSH не является восстановлением после аварии диска/ОС.

Один сеанс наблюдения ограничен четырьмя часами; задача на VPS этим не останавливается. Запустите команду продолжения, чтобы снова подключиться к её наблюдению. Ошибка серверной задачи остаётся ошибкой: `--resume` не скрывает её и не повторяет удаление/развёртывание вслепую. В таком случае нужны диагностика и отдельное решение по исправлению.

Файлы скачиваются во временный путь, проверяются по SHA-256 и только затем заменяют окончательный файл. После обрыва передача повторяется целиком; дозагрузки с байтового смещения нет. Ранее полученная полная копия сохраняется до успешной проверки новой. Файлы загружаются на VPS через временный путь и проверку SHA-256 до переименования; успешно завершённая загрузка фиксируется журналом.

Если прервана защита SSH, повторный вход остаётся обязательным. Не подтверждённая настройка восстанавливается из сохранённого исходного SSH-конфига и получает новый таймер отката; уже подтверждённый этап не переустанавливается. После согласованной перезагрузки сохраняется исходный boot ID: продолжение ожидает новый запуск и проверяет службы, не запрашивая ещё одну перезагрузку.

Журнал содержит адреса, пути к ключам и ответы мастера, **но не содержимое SSH-ключей**. Храните всю папку результатов приватно и не редактируйте журнал вручную. Одновременно использовать один журнал двум процессам запрещает локальная блокировка. Завершённый журнал повторно не выполняется.

Нужна **та же версия кода**, которой начата операция. Готовая команда ссылается на её локальный каталог, в том числе на распакованный переносимый пакет. Не удаляйте этот каталог, исходный SSH-ключ и используемый архив. Запуск latest после нового релиза может скачать другую версию: для продолжения используйте сохранённую команду. Старые операции, начатые до появления session.json, автоматически восстановить этим способом нельзя.

Реализация проверена локальными тестами с изоляцией SSH/systemd/APT/Docker, включая повторный запуск двухсерверного мастера. Реальное Linux-испытание обрывов ещё требуется.

### Два режима: один VPS или основной VPS через российский relay

Сначала выбирается операция: новая установка, восстановление, только бэкап либо обслуживание существующего VPS (пункт 4). Для установки и восстановления затем доступны **ровно два режима подключения**:

1. **Один сервер**: прежний набор VPN плюс Self-Steal на основном VPS, без российского сервера.
2. **Два сервера**: тот же набор на основном VPS, а российский VPS принимает и пересылает подключения. Этот режим выбран по умолчанию.

Self-Steal добавляется к прежнему набору, а не заменяет его. Новые файлы: `selfsteal-vless`, `selfsteal-xhttp`, `selfsteal-hysteria2` в configurations/ и strings/ каждой роли personal/shared. Старые XRay, AmneziaWG, Telegram, WireGuard, OpenVPN, Shadowsocks и Hysteria2 сохраняются. При восстановлении их ключи и пользователи сохраняются из копии; адреса обновляются. Если в старом профиле записан прежний IP, на устройстве потребуется обновить адрес либо импортировать обновлённый профиль.

Схема с relay:

```text
Клиент → российский relay (пересылка TCP/UDP без расшифровки)
       → основной VPS → интернет
```

Приоритет: **AmneziaVPN и её контейнеры → новые способы → остальные**. Amnezia XRay сохраняет прямой TCP 443, конфигурацию и UUID; новый вход не перехватывает её SNI. Для VLESS TLS/Vision и XHTTP используется отдельный TCP-порт, для Hysteria2 — такой же UDP-порт, по умолчанию 8443. Дополнительные варианты REALITY на собственный сайт используют TCP 8444. HAProxy обслуживает только новые способы. Обычные HTTPS-запросы на этот порт открывают сайт Nginx. Разные транспорты сохраняются как разные варианты.

Для relay мастер запросит адрес, SSH-порт и путь к ключу **каждого** VPS. Основной сервер настраивается через SSH ProxyJump на российском: прямой доступ к зарубежному IP с компьютера не обязателен. Приватные ключи остаются на компьютере; SSH-agent на relay не пересылается. При создании бэкапа старого VPS тоже можно выбрать SSH через уже доступный relay без настройки VPN-пересылки на нём.

До запуска направьте A-запись домена на российский relay, а в режиме одного сервера — на основной VPS. AAAA и CDN-проксирование должны быть выключены. Нужны два разных публичных IPv4, назначенных интерфейсам соответствующих VPS (внешний NAT не поддерживается), и чистый relay без существующего VPN/контейнеров и без занятых пересылаемых портов. SSH relay должен использовать отдельный порт, не пересекающийся с пересылкой. SSH-туннелирование до основного VPS должно быть разрешено сервером relay. Firewall провайдера также должен пропускать выбранные TCP/UDP-порты; API провайдера и DNS программа не меняет.

После показа плана потребуются отдельные подтверждения `DEPLOY <IP основного VPS>` и `RELAY <IP российского VPS>`. Сначала проверяются оба сервера, затем включаются постоянные правила пересылки на relay, после этого разворачивается основной VPS и выпускается сертификат через пересылаемый TCP 80. Сертификат остаётся на основном VPS. Настраиваются Fail2ban и вход только по ключу на обоих серверах с проверкой нового SSH-входа и таймером отката SSH.

В профиле **all**, выбранном по умолчанию для сохранения старых доступов, relay пересылает TCP 80, 443, 50553, 6659, 8388–8389 и UDP 443, 46872, 51820, 1194, 2443, 8388–8389. Также пересылается отдельный TCP/UDP-порт новых способов (по умолчанию 8443). Публичные нестандартные порты из манифеста старой копии также добавляются. Их список фиксируется в JSON операции. Правила не охватывают новые случайные порты, которые вы впоследствии создадите в 3DP: для них потребуется обновить пересылку и firewall. Панель 3x-ui на 2053 закрывается на loopback и связывается с 3DP через внутреннюю сеть Docker. Панель 3DP на 6659 остаётся публичной только в all.

Для минимального публичного набора выберите **filtered**: relay пересылает TCP 80/443, отдельный TCP/UDP-порт TLS/Hysteria2 и TCP-порт новых REALITY-вариантов. Старые VPN при этом установлены, но их отдельные порты закрыты. Публикация старых протоколов в all сохраняет их прежние сетевые признаки: маскировка нового профиля не скрывает остальные открытые порты.

На основном VPS отдельная цепочка DOCKER-USER ограничивает управляемые VPN-порты источником relay. Это дополняет UFW, поскольку опубликованные порты Docker могут обходить обычные входящие правила UFW. Правила только собственных цепочек сохраняются через systemd; общий firewall не очищается. Пересылка не добавляет второго шифрования и ограничений полосы. Дополнительный сетевой участок, NAT, TCP-маршрутизатор, нагрузка VPS и маршрут всё равно могут влиять на скорость и задержку; замеров производительности пока нет.

Код находится в пакете `vps_migration/`. В корне оставлены только совместимые точки входа, обёртки запуска, документация и tests/.

```text
scripts/migration/
  migrate.py                 запуск мастера
  remote.py                  запуск серверного worker
  build_portable.py          запуск сборщика
  deploy.ps1, deploy.sh      локальные обёртки
  tests/                     проверки
  vps_migration/
    cli/                     wizard.py, console.py, topology.py
    core/                    common.py
    server/                  worker.py, stack.py, snapshot.py, relay.py, selfsteal.py, selfsteal_features/
    packaging/               build.py, portable.py
      templates/             run.ps1.in, run.sh.in
```

| Каталог | Ответственность |
| --- | --- |
| cli/ | Мастер, меню, проверка ввода, SSH/ProxyJump и выбор схемы. |
| core/ | Общие функции, записи файлов, ключи, Docker API и политика публикации портов. |
| server/ | Развёртывание VPN, relay, Self-Steal, бэкапы и проверки на Linux VPS. |
| packaging/ | Переносимый пакет, сборка релиза и шаблоны запускателей. |
| tests/ | Локальные проверки поведения и целостности пакетов. |

Прежние команды `python scripts/migration/migrate.py`, `python scripts/migration/build_portable.py` и удалённые curl/PowerShell-команды сохраняются. Серверный комплект загружается с пакетной структурой; постоянный relay запускается как Python-модуль из собственного рабочего каталога. В runtime-пакет не попадают тесты и инструменты сборки. Список разрешённых файлов хранится в packaging/portable.py.

В конце проверяются контейнеры, PostgreSQL, HTTPS и авторизация 3DP, старые XRay/Hysteria2, а также новые VLESS TLS, XHTTP и Hysteria2 для personal/shared. Новые тесты соединений и запрос сайта идут на публичный домен, то есть при relay проходят через оба VPS. Это проверяет путь от основного сервера через публичный вход; работу с телефона в конкретной сети провайдера всё равно проверяйте отдельно. Для AmneziaWG/OpenVPN и остальных старых протоколов автоматического клиентского теста нет; статус работающего контейнера не равен рабочему VPN.

Остановка пересылки: `systemctl stop vps-relay.service` на relay; возобновление: `systemctl start vps-relay.service`. Остановка удаляет только собственные правила и возвращает прежнее значение ip_forward. Сведения об операции сохраняются локально в relay-operation.json. Остановка relay не удаляет основной VPS и его доступы. При ошибке последующего развёртывания успешно настроенный relay остаётся на месте — автоматического удаления обоих VPS нет.

Резервная копия включает дополнительные контейнеры и настройки. Восстановление сохраняет Self-Steal UUID/пароли. При миграции старой общей схемы vpn-edge переносится на отдельный порт, а известная локальная публикация Amnezia 1443 возвращается на 443. Новые ссылки переэкспортируются с выбранным портом; на устройствах их нужно обновить. Если прежний отдельный порт свободен, он сохраняется; иначе выбирается свободный в диапазоне 8443–8543 с учётом портов копии. Host/container network и IPv6 Docker-сети по-прежнему требуют ручного плана. Порты и схема показаны до DEPLOY. Полный режим добавляет отдельный WARP-профиль и собственные HTTPS-подписки. Автоматического добавления профилей в 3DP нет.

По решению пользователя БД остаётся **PostgreSQL**. При проверке 27.11.2026 стабильный официальный 3DP — v3.0.0; текущие опубликованные digest backend/frontend совпали с уже закреплёнными в сценарии. Поддержки SQLite в проверенных официальных ветках нет, собственная адаптация не создаётся. Источники: [релизы 3DP](https://github.com/denpiligrim/3dp-manager/releases), [официальная конфигурация БД](https://github.com/denpiligrim/3dp-manager/blob/v3.0.0/server/src/app.module.ts), [гайд Self-Steal](https://denpiligrim.ru/guides/self-steal), [видео автора](https://www.youtube.com/watch?v=cFOou-7pO24).

**Граница проверки:** локальные тесты и проверка новых конфигураций официальным Xray выполнены. Полное развёртывание двух Linux VPS, ACME, реальные iptables/systemd и производительность в целевой сети ещё не испытаны. Перед основной миграцией нужен пробный запуск. Ни Self-Steal, ни российский relay не гарантируют отсутствие блокировки IP.

Пути к SSH-ключу и архиву можно вставлять с внешними кавычками или без них. Системные bind mounts `/lib/modules` и `/usr/lib/modules` сохраняются как подключения каталогов целевого сервера, но их содержимое не копируется: модули должны соответствовать ядру нового VPS. Остальные ограничения на архивирование системных каталогов сохраняются.

### Профиль для сети с фильтрацией и скорость

Профиль `all` сохраняет доступность старых VPN. `filtered` оставляет TCP 443 Amnezia, TCP/UDP-порт TLS/Hysteria2, TCP-порт нового REALITY, SSH и HTTP для сертификата; остальные порты локальны. Relay пересылает пакеты без расшифровки. Скорость зависит от маршрута и нагрузки; замеры на устройстве ещё нужны.

Помимо VPN остаются доступны SSH и TCP 80 для выпуска/продления сертификата. В filtered панели и остальные VPN установлены, но опубликованы только на loopback. Их конфиги экспортируются на будущее и удалённо работать в этом режиме не будут. Публичные подписки 3DP также недоступны. Файл `access/network-profile.txt` напоминает о выбранном режиме. Вариант `all` сохраняет обычную публикацию всех VPN-портов и панели 3DP. Старые JSON-запросы без `network_profile` используют `all` для совместимости.

Для прежнего XRay/REALITY укажите отдельный HTTPS-сайт; новый Self-Steal использует сертификат собственного домена. Новый сервер проверит его сертификат, TLS 1.3 и HTTP/2 по IPv4 и отклонит цель, ведущую обратно на VPS. При восстановлении проверяется фактическая цель из копии; ключи и SNI сохраняются. Доступен выбор клиентского fingerprint `firefox` или `safari`; значение попадает в JSON и ссылку. Условия выбора цели описаны в [документации Amnezia](https://docs.amnezia.org/documentation/instructions/xray-settings/). Проверка совместимости цели не доказывает доступность VPN у вашего провайдера.

REALITY маскирует свойства протокола, но адрес VPS остаётся виден. Блокировку целого IP или подсети этим скрыть нельзя. Защиты от повторной блокировки и отсутствия потерь скорости программа не обещает. Эти изменения проверяются локально; испытания под реальной фильтрацией ещё требуются.

Для локальной HTTP-панели 3x-ui используйте SSH-перенаправление `ssh -i <key> -L 12053:127.0.0.1:2053 root@<new-ip>` и откройте её исходный путь через `http://127.0.0.1:12053/`. Для HTTPS-панели 3DP: `ssh -i <key> -L 16659:127.0.0.1:6659 root@<new-ip>`. Проверка с сохранением домена сертификата: `curl --resolve <domain>:16659:127.0.0.1 https://<domain>:16659/`. Для браузера потребуется локальное разрешение домена на loopback в отдельном профиле; не отключайте проверку сертификата и не меняйте глобальное разрешение VPN-домена.

При восстановлении закрытого профиля API локального узла 3x-ui переключается на внутреннюю сеть Docker с сохранением пути. Внешние узлы не меняются. Локальный HTTPS API и контейнеры с host network требуют отдельной настройки: программа откажется продолжать вместо молчаливого ослабления TLS или публикации портов. Новая пустая панель может обращаться к HTTP API узла по `http://3x-ui:2053/<basepath>`.

Для сохранения всех доступов нужна полная копия формата мигратора. Если прежний сервер недоступен, получить новую копию с него нельзя; старые частичные архивы не заменяют полную копию.

### Без Git, одной командой curl

Публичный общий репозиторий: [shambeer/VpsMigration](https://github.com/shambeer/VpsMigration). Клонирование и авторизация GitHub не нужны.

Linux/WSL:

```bash
curl -fsSL https://github.com/shambeer/VpsMigration/releases/latest/download/run.sh | bash
```

Windows PowerShell 5.1+:

```powershell
& ([scriptblock]::Create((New-Object Net.WebClient).DownloadString('https://github.com/shambeer/VpsMigration/releases/latest/download/run.ps1')))
```

Для проверки без SSH добавьте `--check` в конец PowerShell-команды; для Bash используйте `| bash -s -- --check`. Команды запускаются на компьютере с вашим SSH-ключом. Нужны Python 3.11+ и OpenSSH; в Linux также curl и Bash. В PowerShell Bash/WSL не требуется. Для старого PowerShell при ошибке TLS предварительно выполните `[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12`.

Запускатели скачивают пакет из конкретного версионного релиза и проверяют встроенный SHA-256 перед запуском. Временный пакет удаляется после завершения. Первый скачиваемый запускатель требует доверия к владельцу репозитория и GitHub: проверка пакета не является независимой подписью запускателя. Его можно сначала сохранить и прочитать. Интерактивный Bash использует /dev/tty. Приватный SSH-ключ на новый сервер не переносится.

Пакет включает только явно перечисленные runtime-модули пакета vps_migration, совместимые точки входа, README, обёртки и .gitignore; дополнительно загрузчик и манифест. Доступы, архивы, тесты и остальные файлы репозитория в пакет не входят. Каталог версии на Windows: LOCALAPPDATA/VpsSettings/migration/, Linux: XDG_DATA_HOME/VpsSettings/migration/ либо ~/.local/share/VpsSettings/migration/. Код хранится в каталоге версии, а результаты — в выбранной пользователем папке: Рабочий стол, Документы (по умолчанию) либо свой путь. В ней создаётся VpsMigration/<дата-id>/; полный путь выводится до подключения. На Windows учитываются перенаправленные системные папки. Старые бэкапы не перемещаются. Исходный репозиторий не клонируется; изменённый локальный код не перезаписывается, доступы и копии не удаляются.

Для сборки: `python scripts/migration/build_portable.py`. В dist/migration/ создаются пакет, контрольная сумма, два запускателя, команды и release.json. Публикуются только четыре файла release_assets: vps-migration.pyz, vps-migration.pyz.sha256, run.sh, run.ps1. Команды конкретной версии: run-linux.txt/run-windows.txt. Локальная сборка ничего не публикует. Приватные резервные копии не входят в публичный репозиторий и его историю.

### Из локальных исходников

Windows, из корня репозитория:

```powershell
python -X utf8 scripts/migration/migrate.py
```

Linux/macOS:

```sh
sh scripts/migration/deploy.sh
```

Проверка локального синтаксиса без SSH, установки и чтения VPN-доступов:

```sh
python scripts/migration/migrate.py --check
```

Нужны Python 3.11+ с актуальными исправлениями tarfile и OpenSSH на компьютере. На сервере — root-вход по уже установленному ключу, Python 3.11+, systemd, Linux x86_64: Ubuntu 24.04/26.04 либо Debian 12/13. На старом сервере для копирования дополнительно нужен работающий Docker. Это сценарий именно данного набора контейнеров, не произвольного Linux-сервера и не Windows-сервера.

На новой машине: минимум 1.5 GiB RAM и 6 GiB свободного диска, рекомендуется 2–4 GiB RAM и диск с запасом под полный снимок. При восстановлении дополнительно проверяется оценка размера образов и данных из копии. Для её создания старому серверу нужен свободный диск примерно на два размера снимка плюс 1 GiB; зашифрованная копия автоматически не создаётся.

Заранее направьте все A-записи домена на IPv4 входа (российского relay либо основного VPS), уберите AAAA для этого домена и отключите CDN-проксирование. Откройте нужные порты также в firewall провайдера. В этой версии сценарий рассчитан на IPv4. Новый сервер должен быть чистым: существующие контейнеры, тома с совпадающими именами и непустые пути состояния не перезаписываются.

## Что спросит сценарий

1. Режим: новая установка, перенос либо только резервная копия.
2. IPv4, SSH-порт и путь к приватному SSH-ключу. Содержимое ключа не вставлять.
3. Для переноса — создать свежую полную копию старого сервера либо выбрать готовый migration-bundle.tar.gz и его SHA-256 из backup-result.json.
4. Домен, сайт для маскировки новых REALITY/Telegram-подключений и необязательный email Certbot.
5. Выбор одного VPS или пары с российским relay, доступы к обоим серверам и профиль публикации портов.
6. Подтверждение `BACKUP IP` перед остановкой источника, `DEPLOY IP` перед изменением основного VPS и `RELAY IP` перед настройкой российского сервера. Последнее включает согласие с [условиями Let’s Encrypt](https://letsencrypt.org/repository/), указанными также в приглашении.

Отпечаток нового SSH-сервера подтверждается обычным диалогом OpenSSH; сверяйте его с консолью провайдера. Проверки ключей хоста не отключаются. Для зашифрованного приватного ключа рекомендуется заранее загрузить его в ssh-agent через ssh-add: иначе OpenSSH может повторно спрашивать парольную фразу при отдельных соединениях. Это парольная фраза локального ключа, не пароль сервера.

## Режимы

### Новая установка

Создаются независимые personal/shared-доступы для протоколов и следующие сервисы:

| Сервис | Порт хоста | Назначение |
| --- | --- | --- |
| amnezia-xray | 443/tcp напрямую | VLESS/REALITY; действующие доступы не заменяются новыми транспортами. |
| amnezia-awg2 | 46872/udp | AmneziaWG с отдельными ключами клиентов. |
| amnezia-telemt | 50553/tcp | Telegram MTProxy с Fake TLS. Это прокси Telegram, не системный VPN. |
| vpn-wireguard | 51820/udp | Резервный WireGuard. |
| vpn-openvpn | 1194/udp | Резервный OpenVPN с собственной CA, клиентскими сертификатами и tls-crypt. |
| vpn-shadowsocks | 8388–8389/tcp+udp | Shadowsocks, отдельный порт и пароль для каждой роли. |
| vpn-hysteria2 | 2443/udp, если восстановлен из копии или Self-Steal выключен | Сохранённые доступы; при новой установке с Self-Steal второй одинаковый Hysteria2 не создаётся. |
| 3x-ui | 127.0.0.1:2053/tcp | Панель с новым паролем и случайным базовым путём, доступ через SSH-туннель. |
| 3dp-frontend | 6659/tcp | HTTPS-панель 3DP с новым паролем. |
| 3dp-backend и 3dp-postgres | Только Docker-сеть | Backend и PostgreSQL без публикации их портов. |

80/tcp используется для получения/продления сертификата. SSH-порт берётся из текущего соединения. Остальные внешние входящие соединения закрывает UFW. Docker-публикация портов имеет собственные правила и может обходить UFW: сценарий публикует намеренно только перечисленные порты, а не полагается на UFW для ограничения панелей.

Панели устанавливаются с пустыми новыми базами; узлы, подписки и динамические inbounds 3DP/3x-ui автоматически не создаются. Готовые протоколы выше разворачиваются независимо от панелей и экспортируются напрямую. Для переноса существующих подписок нужен режим восстановления. При последующей самостоятельной настройке панели новые VPN-порты не появятся снаружи автоматически.

Точные версии 3x-ui и 3DP закреплены в stack.py по digest ранее использованных образов. Для остальных новых образов используются реестровые теги; фактически скачанные ID и RepoDigests фиксируются на сервере в /opt/vps-stack/image-lock.json. Это не обещание неизменности latest и не автоматическое обновление уже установленных контейнеров. Образ вспомогательных инструментов собирается из Debian-пакетов. Удалённые install.sh через curl | sh не выполняются.

### Перенос из полной копии

Сценарий сохраняет текущие версии и пользователей, а не обновляет весь стек одновременно с переносом:

- На источнике выбираются семь основных контейнеров и уже существующие четыре резервных сервиса. Сторонние контейнеры и остановленные артефакты старых откатов не включаются.
- Ротация 3DP временно приостанавливается; ожидается завершение активных заданий. Затем сначала останавливаются frontend/backend и панель, база — последней. Полный снимок может занять минуты и больше, зависит от данных и диска. Создаются снимки writable layer контейнеров через docker commit/save, архивы обычных локальных томов и нужных bind-каталогов. PostgreSQL копируется в остановленном состоянии вместе с его точным образом. На время копирования не менять узлы и пользователей вручную.
- Копирование и развёртывание выполняются отдельными systemd-задачами, чтобы продолжиться при обрыве SSH. Это важно, если компьютер подключён через переносимый VPN: при остановке VPN связь исчезнет. Клиент наблюдает за задачей с повторными подключениями; при необходимости переподключите свой VPN после запуска исходных сервисов.
- В finally исходные контейнеры запускаются снова, PostgreSQL — первым, и восстанавливается прежняя ротация, в том числе при обычной ошибке создания копии. Старый сервер не удаляется. Перезагрузка, принудительное убийство процесса или неисправность Docker не покрываются finally: в этих случаях проверить источник через консоль провайдера. Ограничение наблюдения клиента — четыре часа; после него серверная задача может продолжать работу.
- Копия содержит контрольные суммы. Целевая архитектура должна совпадать. Не поддерживаются внешние volume-драйверы, нестандартные сетевые драйверы, пересечение томов с контейнерами вне выбранного набора и перенос произвольных сервисов хоста.
- На чистой цели восстанавливаются образы, данные, сети и контейнерные параметры. Сохраняются пароли и пользовательские UUID. В поддерживаемых настройках, базе 3DP, SQLite TLS-настройках 3x-ui и известных ссылках заменяются адреса/пути нового IP и домена. Секретные поля не должны использоваться как адреса для замены.
- При переносе нынешнего сервера сохраняются личный и общий VLESS-доступы. Если старые клиентские приватные ключи AWG отсутствуют на сервере, восстановить их из публичных ключей невозможно: сценарий добавляет два новых AWG-peer для экспортируемых personal/shared-конфигов, оставляя прежние peer нетронутыми. Если экспорт этого сценария уже был в снимке, используются сохранённые клиентские ключи.
- Telegram-доступы без меток personal/shared экспортируются в legacy/. Старые пароли панели 3x-ui остаются прежними; из хеша пароля нельзя восстановить его текст.
- Отсутствующие WireGuard/OpenVPN/Shadowsocks/Hysteria2 добавляются с новыми доступами. Уже существующие экземпляры с этими именами повторно не создаются.

Нужна полная копия, созданная именно этим сценарием, format=1. Старые архивы частных операций из private-vpn/server-settings/backups/ не содержат всего нужного и напрямую не подходят. Их сценарий не выдаёт за полноценную миграционную копию.

Если старый профиль использует IP, на устройстве потребуется изменить адрес или импортировать обновлённую ссылку: сохранение UUID не перенаправляет старый IP на новый сервер. Тот же домен при смене его A-записи упрощает следующий перенос. Это не перенос DNS-зоны: DNS меняет владелец.

Исходные проблемы сети и неопубликованные динамические порты 3x-ui не исправляются простым копированием. Состояние панелей восстанавливается как было; резервные сервисы публикуются на своих фиксированных портах.

### Только копия

Третий пункт меню создаёт migration-bundle.tar.gz и backup-result.json на компьютере без настройки нового сервера. Копия содержит секреты и не зашифрована. Не публиковать её и не отправлять в Git. Приватные SSH host keys и ~/.ssh источника специально не копируются.

## Защита SSH

Сначала выполняется настоящий вход root с указанным ключом и запрещённым парольным fallback. Приватный ключ используется только локальным OpenSSH. Затем устанавливается Fail2ban с systemd-backend для sshd, портом текущего соединения, пятью попытками за десять минут и баном на час. Текущий административный IP добавляется в ignoreip, чтобы диагностические попытки не заблокировали управление.

Перед защитой SSH проверяется успешный результат именно текущей операции: deploy-result.json для новой установки/восстановления основного VPS, relay-result.json для российского relay. Наличие результата другого этапа, повреждённый JSON и значение success, отличное от булева true, не разрешают изменение SSH. Режим создания бэкапа не запускает hardening. После настройки остаются обязательными новый SSH-вход и подтверждение отмены таймера отката; выбор правильного файла результата не заменяет эти проверки.

После установки сервисов и получения экспортов сценарий добавляет key-only SSH-параметры, проверяет sshd -t и эффективную конфигурацию, ставит rollback timer на 180 секунд и выполняет reload. Старые параметры сохранены. После нового независимого SSH-входа по ключу таймер отменяется; после истечения таймера подтверждение защиты отклоняется. Если связь не вернулась, старый конфиг восстанавливает таймер. Это не полный откат пакетов, UFW и всех VPN, и не замена консоли провайдера.

## Где результат

Локально, внутри исключённой из Git папки:

```text
<выбранная папка>/VpsMigration/<дата-id>/
  migration-bundle.tar.gz
  backup-result.json
  operation.json
  deploy-result.json
  security-result.json
  access-files.tar.gz
  access/
    personal/configurations/<протокол>.json или .conf или .ovpn
    personal/strings/<протокол>.txt
    shared/configurations/...
    shared/strings/...
    admin/...
    legacy/...
```

Некоторые файлы появляются только в соответствующем режиме. У WireGuard/AWG и OpenVPN нет создаваемой этим сценарием универсальной текстовой ссылки: выдаётся нативный конфиг. VLESS/SS/Hysteria2/Telegram получают также URI. Приложения для разных протоколов могут отличаться. Если клиент не поддерживает импорт JSON, используйте VLESS-строку через вставку ключа.

Раздавать только нужные файлы из shared/. Весь архив содержит также личные, административные и прежние доступы. Один WG/AWG peer не подходит для одновременного подключения множества устройств: конечные адреса будут переключаться; для них выдавать отдельные peer. Для массовой раздачи нынешний основной вариант — XRay. Общий OpenVPN-профиль допускает несколько соединений через duplicate-cn; его отзыв затронет всю группу.

Серверные конфигурации новой установки: /opt/vps-stack/config/. Рабочие приватные журналы и скрипты операции: /root/vps-transfer/<дата-id>/. При ошибке смотреть operation.json и last-command-error.log на сервере; скрипт не удаляет частично созданные сервисы, не выполняет массовый prune и отказывается молча перезаписывать их при повторном запуске. Для повторного запуска после сбоя требуется разбор причины или другая чистая машина. Исходные Compose-файлы в перенесённом проекте не являются автоматически обновлённой командой управления восстановленными snapshot-образами.

## Проверки и границы готовности

Финальная локальная проверка 22 ноября 2026 года: 16 тестов прошли, синтаксис Python и PowerShell проверен. Дополнительно проверяются контекст root/Match перед отменой отката SSH, ожидание реального появления пользователя 3x-ui и отклонение multicast/IP вместо домена. Соединение SQLite ожидания закрывается явно, включая Windows. Журнал: private-vpn/server-settings/logs/tools/migration-tests-20261122.log. Это локальные проверки с подменой системных операций, а не запуск Linux-сервера или всех VPN.

При развёртывании сценарий проверяет состояния всех ожидаемых контейнеров выбранной схемы, готовность PostgreSQL, HTTPS 3DP, вход и защищённые API. Временные клиенты выполняют HTTPS-запросы через личный и общий VLESS и Hysteria2; временные контейнеры удаляются. Неуспех останавливает операцию до объявления успеха и до отключения SSH-пароля.

При разработке проверены синтаксис, локальные тесты валидации, безопасной распаковки, сохранения идентификаторов/паролей, экспорта, SSH-параметров, восстановления исходных контейнеров при ошибке, PostgreSQL mount, отклонения позднего SSH commit и вычисления X25519. Полный deploy/restore на чистом VPS не выполнялся. Проверки WireGuard/AWG/OpenVPN/SS с реальных устройств и долговременная стабильность не подтверждены. IPv6 и отсутствие DNS/IPv6-утечек на конкретных клиентах требуют отдельной проверки; установка сервера не даёт такого доказательства.

Перед настоящим переносом выполнить пробный запуск на отдельном чистом VPS с отдельным тестовым доменом: проверить personal/shared по Wi-Fi и мобильной сети, переподключение SSH и Fail2ban, продление сертификата и восстановление из свежей копии. При реальном переносе A-запись рабочего домена должна указывать на новую машину перед целевым развёртыванием; для этого требуется запланированное окно простоя и ожидание обновления DNS. Старый VPS отключать только после успешной проверки нового. Данный документ не является разрешением запускать сценарий на текущем сервере.

Локальные тесты:

```sh
python -m unittest discover -s scripts/migration/tests -v
```

## Обновление ОС и очистка существующего VPS

Пункт **4 — обслуживание** не требует переустановки VPN. Укажите SSH-доступ, при необходимости ProxyJump, затем выберите обновление ОС или очистку. Сначала подтвердите `PLAN <IP>`: программа загрузит служебный код и подготовит план; для обновления также обновит индексы APT.

При новой установке/восстановлении такой же план обновления ОС согласуется для основного VPS и relay до установки. Режим создания копии не обновляет исходный сервер.

### Обновление

План сохраняется в `os-<IP>/os-plan.json`: установки, версии, удаления и удержанные пакеты. В терминале показаны первые 20 изменений и все удаления; полный список откройте в JSON. `UPGRADE <IP>` разрешает весь этот план. Перед применением повторная симуляция обязана совпасть. APT может перезапустить Docker/SSH и временно прервать VPN.

Выполняется `apt-get dist-upgrade` в текущем выпуске Debian/Ubuntu, без смены выпуска ОС и репозиториев. Существующие настройки сохраняются через confdef/confold; пакеты Essential/Protected и критическая инфраструктура защищены от удаления. Если после операции остались обновления, результат считается незавершённым: hold, phased updates и ограничения зависимостей не обходятся автоматически. [Поведение APT](https://manpages.debian.org/unstable/apt/apt-get.8.en.html).

Перед обновлением сохраняются `/etc` и перечень пакетов в `os-config-backup.tar.gz`. Это **не образ диска и не автоматический откат ОС**. Проверяются dpkg, SSH, новые отказы systemd и ранее работавшие контейнеры. После успешного обновления при необходимости предлагается перезагрузка: по умолчанию отложить; запуск только через отдельное `REBOOT <IP>`. Разрешение связано с текущим boot ID. Мастер ждёт другой boot ID и проверяет ядро, службы, Docker и управляемые приложения. Если перезагрузка отложена, полное применение системных изменений не подтверждается.

### Очистка

Выберите контейнеры и пакеты номерами; Enter пропускает категорию. `ALL` выбирает всех показанных кандидатов. Кандидат не означает доказанную ненужность: назначение приложения решает администратор. Предлагаются ручные пакеты и неиспользуемые автоматические зависимости; дополнительное autoremove выключено по умолчанию. Из списка исключаются известные VPN, системная/сетевая/загрузочная инфраструктура и её установленные зависимости. Контейнеры AutoRemove не предлагаются.

После выбора сервер рассчитывает точные удаления APT с зависимостями. Просмотрите `cleanup-plan.json`, подтвердите `DELETE <IP>`. Смена объектов/плана требует нового согласования. Не выполняйте параллельно административные операции APT/Docker во время обслуживания.

До первого удаления создаётся `cleanup-backup.tar.gz`: `/etc`, перечень пакетов, план, Docker inspect и сохранённые образы выбранных контейнеров. Работавшие контейнеры останавливаются для резервирования. При ошибке резервирования программа пытается вернуть их в работу; удаление до готовности копии не начинается. После начала удаления журнал `cleanup-progress.json` позволяет увидеть частичный результат. Автоматического восстановления уже удалённых контейнеров/пакетов нет.

Удаление Docker выполняется без `-v`; тома и bind-каталоги остаются. **Содержимое томов не входит в этот архив**: Docker commit/save сохраняет образ и writable layer, а не полноценную согласованную копию БД. Для миграции данных используйте полную копию мигратора. Пакеты удаляются без purge; программа не удаляет их конфиги, но действия штатных пакетных hooks требуют отдельной оценки. Не выполняются Docker prune, удаление произвольных файлов и очистка pip/npm. Сохранённые данные/образы могут продолжать занимать диск. [Удаление пакетов Debian](https://www.debian.org/doc/manuals/debian-reference/ch02.en).

Архивы обслуживания скачиваются в выбранную локальную папку с проверкой SHA-256; ошибка скачивания выводит путь серверной копии и не считается полным успехом. Это **не format1 bundle** для пункта восстановления. Архивы содержат секретные настройки и не зашифрованы — храните приватно.

Обновление Docker-образов FR-34 по решению пользователя оставлено штатным механизмам приложений. Универсального обновления до latest и автоматической смены major PostgreSQL нет.

Код: `vps_migration/cli/maintenance.py` и `vps_migration/server/maintenance/{apt,cleanup,operations}.py`. Локальные проверки изолируют системные вызовы. Обновление, очистка и перезагрузка реального Linux VPS пока не испытаны.

### Повторные варианты и совместимость

При новой установке с Self-Steal используется один Hysteria2 с TLS, userpass, Salamander и маскировкой под сайт; второй такой же экземпляр на 2443 не создаётся. Без Self-Steal остаётся резервный Hysteria2. AmneziaWG и WireGuard, REALITY, TLS/Vision и XHTTP сохраняются: это разные варианты. Повторный запуск добавления полной схемы экспортирует существующие доступы, не создавая контейнеры повторно; частичная схема требует ручного решения.

При восстановлении существующие контейнеры и доступы не удаляются ради устранения дубликатов: если в копии уже два Hysteria2 с разными ключами, оба сохраняются. Автоматического отзыва/объединения этих доступов нет. При конфликте занятых портов программа выбирает отдельный порт для новых способов или останавливается, не вытесняя Amnezia. Это не автоматическое объединение произвольных приложений из любых контейнеров Amnezia.

## FR-17: полный набор Self-Steal

Новые установки и миграции по умолчанию включают расширенный режим. Приоритет **Amnezia → новые способы → остальные** сохранён. По последнему решению пользователя общий вход на TCP 443 не используется: работающий вход Amnezia остаётся прямым.

| Вариант | Публичный порт по умолчанию | Файлы personal/shared |
| --- | --- | --- |
| VLESS RAW + TLS/Vision | TCP 8443 | selfsteal-vless |
| VLESS XHTTP + TLS | TCP 8443 | selfsteal-xhttp |
| VLESS RAW/HTTP + TLS → WARP | TCP 8443 | selfsteal-warp |
| VLESS RAW + REALITY/Vision на собственный сайт | TCP 8444 | selfsteal-reality |
| VLESS XHTTP + REALITY | TCP 8444 | selfsteal-reality-xhttp |
| VLESS RAW/HTTP + REALITY → WARP | TCP 8444 | selfsteal-reality-warp |
| Hysteria2 + TLS/Sаламандра + сайт | UDP 8443 | selfsteal-hysteria2 |

Те же внутренние XHTTP/WARP-инбаунды обслуживают оба защищённых входа; одинаковые процессы/инбаунды повторно не создаются. Дополнительный Hysteria2 при новой установке не нужен. Существующие доступы и отдельный Hysteria2 из копии сохраняются.

Вход REALITY использует сертификат и TLS-сайт собственного Nginx. Неизвестные клиентские подключения открывают сайт, а fallback направляет XHTTP в Nginx и отдельный HTTP-путь в WARP-инбаунд с PROXY protocol. Nginx принимает HTTP/2 и на резервном входе без ALPN — эта связка проверена реальным локальным запросом. Варианты для старого Amnezia XRay продолжают использовать его прежний SNI и ключи.

### WARP

Программа регистрирует WireGuard-устройство через интерфейс Cloudflare, используемый официальным 3x-ui, и сохраняет результат приватно. Это собственный модуль на основе проверенного интерфейса, а не запуск стороннего shell-скрипта или изменение аккаунта WARP в панели. Перед DEPLOY выводятся сведения о регистрации и [условиях Cloudflare](https://www.cloudflare.com/application/terms/). Регистрация не выполняется при локальном --check.

Выход WireGuard работает внутри Xray без смены таблицы маршрутизации хоста. Только тег нового WARP-инбаунда направляется через него; прочие профили остаются на прямом выходе. При ошибке WARP нет автоматической подмены прямым соединением. Для одного IP используется сохранённая регистрация; при переносе на другой IP создаётся отдельная регистрация выхода, чтобы старый и новый сервер не перетягивали один WireGuard endpoint. Клиентские UUID и REALITY-ключи при этом сохраняются.

Если ответ регистрации потерян, сохранённая pending-попытка не повторяется автоматически: требуется диагностика. Успешная регистрация и доступность реального Cloudflare зависят от сети VPS. При серверной проверке оба WARP-профиля каждой роли обязаны показать warp=on/plus. WARP не является выбором произвольной страны. Источники: [реализация регистрации 3x-ui](https://github.com/MHSanaei/3x-ui/blob/main/internal/web/service/integration/warp.go), [WireGuard outbound Xray](https://xtls.github.io/en/config/outbounds/wireguard.html), [режимы WARP](https://developers.cloudflare.com/warp-client/warp-modes/).

### HTTPS-подписки, Happ и INCY

Каждая роль получает собственный случайный URL в strings/subscription.txt, текстовый и Base64-набор в subscriptions/, а также файлы happ-routing.json/.txt и incy-routing.json/.txt. В приложение добавьте HTTPS-URL подписки, затем при необходимости импортируйте строку маршрутизации соответствующего приложения. Это не QR-код.

Подписки включают поддерживаемые URI VLESS, Hysteria2 и Shadowsocks из папки роли; одинаковые URI с разными метками не повторяются. CONF AmneziaWG/WireGuard, OVPN и Telegram остаются отдельными файлами/ссылками: общего импортируемого URI для них нет. У личной и общей подписки разные токены. Сохраняйте URL как пароль, не публикуйте папку admin/ или весь архив. Nginx не пишет access-log этого сайта/подписок. Стандартная Base64-подписка не гарантирует поддержку всех транспортов старой версией приложения.

По умолчанию напрямую идут только локальные ресурсы и явно указанные direct_domains/direct_networks. Опция guide_whitelist включает профиль белого списка из гайда с закреплёнными версиями внешних GeoIP/Geosite-данных. Это отдельное решение: такие ресурсы обходят VPN. Полноту стороннего списка программа не подтверждает.

### Настройка и свой сайт

Пример — [selfsteal.example.json](selfsteal.example.json). Можно оставить всё по умолчанию либо передать файл:

```bash
python scripts/migration/migrate.py --options /path/to/options.json
curl -fsSL https://github.com/shambeer/VpsMigration/releases/latest/download/run.sh | bash -s -- --options /path/to/options.json
```

```powershell
& ([scriptblock]::Create((New-Object Net.WebClient).DownloadString('https://github.com/shambeer/VpsMigration/releases/latest/download/run.ps1'))) --options 'C:\path\options.json'
```

Поддержаны warp/reality/subscriptions, отдельные tls_port/reality_port, дополнительные SAN-домены, свои пути XHTTP/WARP, параметры packet-up, padding/обфускации, расположения session/seq/uplink, интервалы/размеры POST и XMUX. Сервер и экспортируемые клиенты получают согласованные параметры, включая extra в URI. Внутренние порты изолированы сетью Docker; публичные порты проверяются на конфликты, в том числе с loopback-привязками из копии. Amnezia и существующие сервисы не вытесняются. Порты показываются перед DEPLOY.

Чтобы использовать свой сайт, добавьте site_directory с абсолютным путём к статическому экспорту с index.html. Разрешены обычные статические файлы, не более 5000 объектов/20 MiB; скрытые файлы, ссылки, ключи, базы и серверный код не публикуются. Архив получает SHA-256 и сохраняется в папке операции; --resume использует эту же копию. Динамический PHP/Node-сайт таким способом не разворачивается.

HTTP 80 обслуживает ACME и перенаправляет браузер на HTTPS-порт новых способов. Certbot переводится на webroot с проверкой; начиная с 2.3 используется reconfigure. Для более старого Certbot выполняются dry-run и один принудительный перевыпуск, чтобы сохранить параметры; он учитывается в лимитах CA. До изменения сохраняется renewal-конфигурация. Продление не требует останавливать Amnezia. [Порядок Certbot](https://eff-certbot.readthedocs.io/en/latest/using.html#modifying-the-renewal-configuration-of-existing-certificates).

Мастер также сохраняет access/admin/ssh-tunnel.txt: готовую локальную команду SSH-туннеля к 3x-ui, с учётом ProxyJump. Если в старой копии нет пути панели, используйте её прежний base path вместо /. Ключи не переносятся на VPS. Панели устанавливаются как раньше; новые standalone-профили управляются мигратором, а не автоматически создаются в 3DP/редакторе инбаундов 3x-ui. Автоматизация управления панелями относится к FR-24 и этим изменением не добавлена.

### Проверки и границы

Для полного режима нужен Xray 26.11.9+ и Nginx с поддержкой http2 on (1.25.1+). Старое ядро отвергается до регистрации WARP. Автоматическое обновление восстановленных образов вопреки решению FR-34 не выполняется.

Локально проверены официальным Xray v26.11.9/Nginx 1.28.3 шесть VLESS-вариантов и обе HTTPS-подписки. WARP в этом испытании заменён отдельным тестовым выходом: подтверждено разделение маршрутов, а не реальная регистрация Cloudflare. Автотесты проверяют кэш регистрации, отказ без согласия, повторный запуск, сохранение UUID, защиту путей/сайта, конфигурации и сценарии Certbot. Сервер перед применением проверяет кандидат Xray и Nginx; копия прежних новых настроек — selfsteal-before-features.tar.gz. Она скачивается вместе с другими приватными копиями.

Полная Linux-установка, реальная регистрация WARP, выдача/продление ACME, работа через двухсерверный relay и импорт в приложения телефонов в этой задаче не выполнялись. Ограничителей полосы не добавлено; WARP даёт дополнительный маршрут, а packet-up/padding/интервалы могут влиять на скорость и задержку. Amnezia в эти цепочки не включается.

Состав сверён с [актуальным текстовым гайдом автора](https://denpiligrim.ru/guides/self-steal) и главами [исходного видео](https://www.youtube.com/watch?v=cFOou-7pO24). Страница видео доступна, но сервер субтитров вернул пустой ответ; аудиодорожку целиком проверить не удалось. Это не заявление о буквальном повторении всех действий автора в интерфейсе панели.
